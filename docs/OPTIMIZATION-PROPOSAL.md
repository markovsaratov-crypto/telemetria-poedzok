## 1. Диагноз: где сейчас узкие места (факты, не гипотезы)

| Компонент | Факт | Последствие |
|---|---|---|
| **D1 (free)** | Дневная квота 5 млн строк-чтений; выгорала **три дня подряд** (15.09 частично, 16.09 — инцидент §5а, 17.09 — повторно до деплоя v2.38.2) | `db degraded` до 00:00 UTC, дашборды без данных |
| **Render (free)** | 1 инстанс, засыпание при простое, ~0.5 CPU / 512 МБ; все кэши in-memory (trip-stats, RouteCache, agg-cache, rate-limit) живут ровно до рестарта/сна | Холодные старты, потеря кэшей → повторные full-read после каждого пробуждения; 4 cron-сервиса дёргают инстанс 5+/час, мешая сну |
| **d1-gateway Worker** | SQL-over-HTTP; каждый SQL — HTTP-хоп Франкфурт↔CF-edge; rate-limit в памяти изолейта | +50–150 мс на каждый SQL; лимиты/счётчики не переживают рестарты изолейтов |
| **UI → origin** | Все API-запросы идут на Render во Франкфурт (TurboFlare кэширует только статику); дашборд поллит `/api/trips/batch` каждые 30 с | ~100–200 мс RTT на запрос из РФ; постоянный фоновый трафик |
| **Данные** | GpsPoint — десятки тысяч строк и растёт; статы/дашборды считаются конвейером по точкам | Чтения D1 растут линейно с объёмом данных и числом вкладок |

**Вывод:** узкое место №1 — **путь чтения** (дашборды пересчитывают/перечитывают
агрегаты по сырым точкам), №2 — **география** (логика в Франкфурте, пользователь
в РФ, БД на edge), №3 — **эфемерность free-инстанса** (кэши и cron-архитектура).

## 2. Принципы (практики, на которых построены варианты)

1. **Read-path ≠ write-path (CQRS-lite):** пишем в OLTP-таблицы, читаем из
   предвычисленных агрегатов — никогда не агрегируем сырьё на запросе.
2. **Materialized rollups:** агрегат обновляется событием (финализация сессии),
   а не пересчитывается на лету при каждом просмотре.
3. **Многоуровневый кэш с явной инвалидацией:** edge (CDN/Worker) → memory →
   БД; TTL + invalidation-by-event, а не «кэш навсегда».
4. **Edge-first:** обрабатывать запрос максимально близко к пользователю.
5. **Backpressure и идемпотентность** на инжесте: пик не роняет систему,
   повтор — безопасен.
6. **Observability-first (USE/RED):** сначала метрики (p95, cache hit, квоты),
   потом оптимизация; каждое изменение проверяется числом, не ощущением.
7. **Конфигурация поверх кода:** все TTL/лимиты — env-переменные.

## 3. Вариант A — «Быстрые победы» (0 ₽, ~1–2 недели, без смены платформы)

| # | Мера | Практика | Ожидаемый эффект |
|---|---|---|---|
| A1 | **Rollup-таблица** `StatsRollup(day, userId, sessions, points, distance, duration, ecoSum …)`: инкрементальное обновление при финализации сессии; дашборды читают O(дней) строк вместо O(точек) | materialized view / pre-aggregation | **−80…95 % чтений D1** на дашбордах; главный удар по квоте |
| A2 | **HTTP-кэширование ответов:** `ETag` + `Cache-Control: private, max-age=30, stale-while-revalidate=60` на `/api/stats`, `/api/trips/*`; 304-ответы почти бесплатны | HTTP caching / SWR | −50…70 % запросов к origin при открытой вкладке |
| A3 | **Умный опрос:** интервал 30 с → 60 с + exponential backoff при 429/5xx + пауза при `visibilitychange` (вкладка скрыта — не поллить) | adaptive polling | −30…50 % фонового трафика; квота живёт дольше |
| A4 | **Бюджетный warmup после старта:** прогрев top-N сессий (например, 20 последних) сразу после boot, а не лениво первым пользователем | cache priming | Первый пользователь не платит холодным кэшем |
| A5 | **Фронтенд-скорость:** prefetch при hover, virtualization длинных таблиц, `content-visibility` для тяжёлых секций, бюджет Lighthouse в CI (perf ≥ 90) | RUM/perf budgets | INP/LCP ↓, плавность на мобильных |
| A6 | **Гигиена квоты:** алерт на 70 % дневного лимита `d1_rows_read_total` (Slack уже подключён) — узнать о проблеме до 500-х | error budget | Инцидент ловится до деградации |

## 4. Вариант B — «Data-plane на Cloudflare» (0 ₽ в free tier, ~2–4 недели, поэтапно)

| # | Мера | Практика | Эффект |
|---|---|---|---|
| B1 | **Edge-инжест:** роут `/ingest` прямо в d1-gateway-воркере (валидация батча + многорядный INSERT в D1); Render исключается из горячего пути записи | edge compute | Латентность инжеста −50 %+ (edge рядом с РФ); нагрузка Render −60…80 % |
| B2 | **KV для горячих агрегатов:** ключ `dash:{userId}:{day}` → JSON, TTL 30–60 с, инвалидация при финализации; чтения KV не тарифицируются D1-квотой (free: 100k reads/день ≫ потребности дашбордов) | cache-aside + CDN-уровень | Чтения D1 на дашбордах → почти 0 |
| B3 | **Durable Objects (SQLite-backed)** для rate-limit, счётчиков, состояния воркера | single-writer state | Честные лимиты, переживают рестарты изолейтов |
| B4 | **Cloudflare Queues** для пиков инжеста: продюсер = edge-роут, консьюмер = батчи в D1; ретраи и DLQ из коробки | queue-based leveling | Пики не выжигают квоту записи, backpressure бесплатно |
| B5 | **Cron Triggers в воркере** вместо 4 cron-сервисов Render (retention/alerts/backup/finalize) | scheduled compute | Не будят Render, не торчат наружу с CRON_SECRET; минус 4 сервиса |
| B6 | **Next.js на Cloudflare** (`@opennextjs/cloudflare`, Workers/Pages): весь сайт на edge; Render удаляется (или остаётся admin-origin на переходный период) | edge-first deployment | TTFB −50…70 % для РФ; нет засыпания и холодных стартов; нет межконтинентального SQL-хопа для инжеста |
| B7 | **Наблюдаемость:** Workers Analytics Engine (per-route p95/p99), Logpush; алерты в Slack уже есть | RED-метрики | Видно эффект каждого шага в числах |

**Риски B и их закрытие:** перенос бизнес-логики в воркер (закрывается
юнит-тестами ядер — они уже 50/50 и платформо-независимы); миграция секретов
(рунбук уже есть); совместимость Prisma↔D1 (уже доказана v2.37+). Путь
поэтапный: **B1 → B2 → B5 → B6**, каждый шаг — отдельный деплой с откатом,
ничего «большим взрывом».

|---|---|---|---|

## 6. Сравнение вариантов

| Критерий | A — быстрые победы | B — edge | C — платформа |
|---|---|---|---|
| Стоимость | 0 ₽ | 0 ₽ (free tier) | 0–20 $/мес |
| Чтения D1 (дашборды) | −80…95 % | → ~0 (KV) | квот нет |
| p95 API / скорость UI | −30…50 % | −50…70 % (РФ) | −20…40 % |
| Нагрузка Render | −30 % | −60…80 % (до 0 при B6) | −30 % |
| Риск | низкий | средний (поэтапный, обратимый) | высокий (миграция) |
| Усилия | 1–2 недели | 2–4 недели | 4–8 недель |
| Обратимость | полная | полная, по шагам | ограниченная |

## 7. Рекомендуемый путь

1. **Этап 1 — вариант A целиком** (A1–A6): закрывает инциденты квоты уже
   текущими бесплатными лимитами; не трогает архитектуру.
2. **Этап 2 — B1 + B2 + B5:** инжест и горячие чтения уходят на edge, Render
   перестаёт быть бутылочным горлышком.
3. **Этап 3 — B6** при росте аудитории (или при желании убрать Render).
4. **C** — только при упоре в потолок объёмов/аналитики.

**Метрики успеха этапов (числа, не ощущения):**
- `d1_rows_read_total` ≤ 1 млн/день при текущем трафике (контроль `/api/metrics`);
- p95 `/api/stats` ≤ 300 мс;
- Lighthouse Performance ≥ 90 (mobile);
- 0 инцидентов квоты D1 за 30 дней подряд;
- cache hit ratio ≥ 70 % на A2/B2.

## 8. Чего НЕ делать (анти-паттерны)

- не «чинить» отзывчивость учащением опроса — именно это выжгло квоту;
- не складывать кэш в D1-таблицу (чтение кэша = расход той же квоты) — для этого KV;
- не строить свою очередь поверх D1 — есть Queues;
- не оптимизировать вслепую: сначала метрика, потом изменение, потом diff метрики.
