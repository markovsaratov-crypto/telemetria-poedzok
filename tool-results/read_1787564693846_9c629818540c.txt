   123→1.1 Назначение
   124→Сервис «Телеметрия поездок» предназначен для непрерывного сбора, хранения и анализа GPS-данных
   125→автомобильных поездок. Основная ценность системы заключается в план-фактном анализе: сервис
   126→сравнивает фактически пройденный маршрут с заранее запланированным, вычисляя отклонения по
   127→каждому сегменту пути, длительности, скорости и пробковым условиям. Это позволяет оценивать
   128→эффективность маршрутизации, качество дорожной инфраструктуры и поведение водителя в реальных
   129→условиях.
   130→Система ориентирована на личное использование: владелец устанавливает приложение Sensor Logger на
   131→iPhone, которое записывает GPS-координаты с высокой частотой. Данные автоматически отправляются на
   132→сервер через API-эндпоинт ingest. Веб-интерфейс позволяет просматривать поездки на карте,
   133→анализировать скорость, выявлять проблемные участки и сравнивать план с фактом. Все данные хранятся
   134→в базе SQLite (Turso/LibSQL), что обеспечивает простоту развёртывания и минимальные операционные
   135→затраты.
   136→1.2 Ключевые возможности
   137→• Сбор GPS-треков из Sensor Logger (iPhone) через HTTP API с Bearer-авторизацией и
   138→идемпотентной передачей (clientId).
   139→• Автоматическая маршрутизация через API 2ГИС (carrouting 6.0.0) с fallback на OSRM и гаверсинус.
   140→• Исторические данные о пробках по каждому сегменту маршрута — обработка выделена в
   141→отдельный Worker-процесс.
   142→• План-фактный анализ: отклонение по длительности, скорости и дистанции для каждого сегмента.
   143→• Веб-интерфейс с декомпозированными компонентами, интерактивной картой (Leaflet) и 4 вкладками
   144→телеметрии.
   145→• Управление избранными маршрутами (сохранение, удаление, использование при планировании).
   146→• Двухуровневое кэширование результатов маршрутизации (in-memory LRU + SQLite persistent) с
   147→округлением до сетки ~55 м × ~35 м (snap-to-grid) и time-of-day-ключом.
   148→• Cursor-based пагинация GPS-точек для эффективной загрузки больших сессий.
   149→• Структурированное логирование (pino), Prometheus-метрики и health-check.
   150→• Zod-валидация всех входных данных, payload-лимиты (256 КБ), p-limit concurrency control, CORS

   152→• Backward-compatible миграции БД по паттерну expand-contract; CI/CD-конвейер с
   153→автоматическими тестами.
   154→• Rate limiting на Redis sliding window (multi-instance) с fallback на in-memory для single-instance.
   155→• STRIDE threat model (18 угроз), политика деградации 2ГИС→OSRM→гаверсинус с circuit breaker
   156→и уведомлением пользователя, 3-уровневый backup (Turso snapshots + logical dump + on-demand
   157→export) с RPO 1ч / RTO 30мин.

   397→2.4 Middleware
   398→Единый middleware-слой (src/middleware.ts) обеспечивает сквозную обработку всех API-запросов.
   399→Шаг проверки размера payload (256 КБ для ingest) — запросы превышающие лимит отклоняются с HTTP
   400→413 до попадания в route-handler, что защищает event loop от парсинга oversized JSON. Middleware
   401→выполняется до каждого route-handler и реализует: (а) payload-size guard — Content-Length проверка до
   402→чтения body; (б) авторизацию — проверка Bearer-токена или HttpOnly-куки; (в) rate limiting — sliding
   403→window через Redis (production) или in-memory (dev); (г) CORS; (д) security headers; (е) requestId; (ж)
   404→логирование method/path/duration/status.
   405→src/middleware.ts — async function с импортами и try/catch

   407→import { NextRequest, NextResponse } from "next/server";
   408→import { checkRateLimit } from "@/lib/rate-limit";
   409→import { authenticate } from "@/lib/auth";
   410→import { corsResponse, setSecurityHeaders } from "@/lib/http-utils";
   411→import { json } from "@/lib/http-utils";
   412→import { logger } from "@/lib/logger";
   413→const MAX_PAYLOAD_BYTES = Number(process.env.MAX_PAYLOAD_BYTES ?? 262144);
   414→export async function middleware(request: NextRequest): Promise {
   415→const requestId = crypto.randomUUID();
   416→const start = Date.now();
   417→try {
   418→// 0. payload-size guard (до чтения body)
   419→const cl = Number(request.headers.get("content-length") ?? 0);
   420→if (cl > MAX_PAYLOAD_BYTES) {
   421→return json({ error: "Payload too large", limit: MAX_PAYLOAD_BYTES }, 413);
   422→}
   423→// 1. CORS preflight
   424→if (request.method === "OPTIONS") return corsResponse(request);
   425→// 2. Rate limit check (Redis sliding window / in-memory LRU)
   426→const rateResult = await checkRateLimit(request);
   427→if (!rateResult.allowed) {
   428→return json(
   429→{ error: "Rate limit exceeded", retryAfter: rateResult.retryAfter },
   430→429,
   431→{ "X-RateLimit-Limit": String(rateResult.limit),
   432→"X-RateLimit-Remaining": String(rateResult.remaining),
   433→"X-RateLimit-Reset": String(rateResult.reset) }
   434→);
   435→}
   436→// 3. Authentication (Bearer token or HttpOnly cookie)
   437→const authResult = authenticate(request);
   438→if (!authResult.ok) {
   439→return json({ error: "Unauthorized" }, 401);
   440→}
   441→// 4. Security headers + requestId
   442→const response = NextResponse.next();
   443→setSecurityHeaders(response);

   499→2.6 Изоляция Worker-процесса
   500→Изоляция Worker-процесса от API event loop
   501→TrafficJob обрабатывается в отдельном Worker-процессе. Если бы обработка шла in-process (в том же
   502→Node.js-процессе, что и API), при 100 сессиях/мин (100 × ~50 сегментов = 5000 fetch) event loop API-сервера
   503→забивался бы сетевыми I/O, и ingest переставал отвечать. Выделение Worker-процесса решает эту проблему.
   504→API-сервер и Worker-процесс — два независимых процесса. API-хендлер POST /api/ingest
   505→выполняет только синхронные быстрые операции: Zod-валидация, проверка идемпотентности, INSERT
   506→GPS-точек (одна транзакция), INSERT строки в TrafficJob со статусом pending. Ответ клиенту
   507→возвращается немедленно (HTTP 201 за ≤ 50 мс типично), после чего event loop свободен для следующего
   508→ingest-запроса.
   509→Worker-процесс (worker/index.ts) — отдельный Node.js-процесс, запускаемый параллельно с
   510→API-сервером (Docker compose: два сервиса; Vercel: serverless-функция по Cron). Worker опрашивает
   511→таблицу TrafficJob с интервалом WORKER_POLL_INTERVAL_MS (по умолчанию 5 с), выбирает пачку
   512→pending-задач (LIMIT 10), атомарно захватывает их через UPDATE ... SET status='running',
   513→lockedBy=$workerId, lockedAt=now() WHERE id IN (...) AND status='pending'
   514→RETURNING id и обрабатывает только те id, что вернулись в RETURNING (см. ниже про
   515→верификацию). Controlled concurrency внутри Worker: p-limit(5) — не более 5 параллельных
   516→traffic-fetch.
   517→Шаг API-сервер Worker-процесс
   518→1 Принимает ingest, Zod-валидация —
   519→2 Проверка идемпотентности (deviceId, clientId) —
   520→3 INSERT GpsPoint[] (транзакция) —
   521→4 INSERT TrafficJob(status=pending) —
   522→5 HTTP 201 → клиенту (≤ 50 мс) —
   523→6 — Опрос: SELECT pending LIMIT 10 (каждые 5 c)
   524→7 — UPDATE ... SET running, lockedBy (атомарный захват)
   525→8 — fetch traffic (2ГИС), p-limit(5), retry×3, backoff
   526→9 — UPDATE TrafficJob SET status=completed, result=...
   527→10 — Если failed: attempts++, backoff, повтор при attempts < 3

   540→При росте очереди Worker-процессы можно масштабировать горизонтально: запустить N инстансов Worker с

   545→При репликации Turso (read-replica) возможна ситуация: Worker A читает pending-задачу из реплики, Worker B из

   549→уже захватил другой Worker, пропуск. Для LibSQL/Turso также рекомендуется BEGIN IMMEDIATE для
   550→write-транзакций захвата, что берёт write-lock на primary до любых SELECT/UPDATE. См. §3.9 — ограничения

   660→3.5 Кэширование маршрутов
   661→Архитектура кэш-ключа маршрутизации
   662→Кэш-ключ строится на основе snap-to-grid координат и time-of-day bucket.
   663→Обоснование snap-to-grid
   664→Snap-to-grid (Math.round(v / GRID_SIZE) * GRID_SIZE) с GRID_SIZE=0.0005° даёт ячейку ~55 м (lat) × ~35 м (lon).
   665→Это превышает точность GPS-приёмника iPhone (5-10 м), делая ключ устойчивым к естественному GPS-шуму: две
   666→точки в пределах одной ячейки дают один ключ, две точки в разных ячейках (расстояние > 35 м) — разные ключи.
   667→Ожидаемый hit ratio — 70–85% (требует подтверждения в k6-тестах, см. §8.4).
   668→Кэш-ключ состоит из двух компонентов. Первый — snap-to-grid координат до сетки с шагом
   669→GRID_SIZE = 0.0005°. На широте Саратова (~51°): 1° широты ≈ 111 200 м (почти постоянно), 1°
   670→долготы ≈ 111 320 · cos(51°) ≈ 70 000 м. Следовательно GRID_SIZE = 0.0005° даёт ячейку ~55 м (по
   671→широте) × ~35 м (по долготе). Второй компонент — time-of-day bucket: час дня округляется вниз до
   672→кратного 3 (8 бакетов: 0, 3, 6, 9, 12, 15, 18, 21 UTC). Маршрут «дом → работа» в 08:00 и в 20:00 получает
   673→разные кэш-записи с разными traffic-данными.
   674→Двухуровневый кэш реализован в src/lib/cache.ts. Уровень 1: in-memory LRU (Map +
   675→doubly-linked list, макс. 100 записей, TTL 5 мин). Уровень 2: persistent в таблице RouteCache (hash, result,
   676→todBucket, routeId, expiresAt, TTL 24 ч). Паттерн cache-aside: сначала LRU, при miss — RouteCache, при
   677→miss — вызов API, результат пишется в оба уровня.

   741→3.6 Идемпотентность ingest
   742→Идемпотентность через clientId
   743→Sensor Logger при сетевом сбое ретранслирует пакет. Без идемпотентности повторная отправка создавала бы новую
   744→сессию с дублированными GPS-точками — данные портились, segmentDeviations считались по «фантомной»
   745→сессии.

   753→TrafficJob.
   754→• Конкуренция: если два одинаковых запроса приходят одновременно (split-brain сети),
   755→UNIQUE-индекс БД гарантированно пропускает только первый; второй получает constraint violation и

  1244→In-memory LRU считает 10 запросов/мин на инстанс. При multi-instance (2 контейнера или 2 serverless функции
  1245→Vercel) каждый считал независимо — суммарно 20 запросов/мин, что пробивает SLA 2ГИС и приводит к 429 от
  1246→самого 2ГИС.
  1247→Введён backend-agnostic rate-limiter с двумя реализациями. Primary — Redis sliding window (через
  1248→ZSET: timestamp как score, подсчёт членов в окне). Рекомендуется Upstash Redis (serverless, REST API,
  1249→бесплатный tier 10K команд/день). Fallback — in-memory LRU (для single-instance dev-окружения).
  1250→Выбор backend конфигурируется переменной RATE_LIMIT_BACKEND=redis|memory.
  1251→src/lib/rate-limit.ts — sliding window на Redis
  1252→// src/lib/rate-limit.ts
  1253→export interface IRateLimiter {
  1254→check(key: string, limit: number, windowSec: number): Promise<{
  1255→allowed: boolean; remaining: number; retryAfter: number;
  1256→}>;
  1257→}
  1258→// Redis sliding window (ZSET)
  1259→class RedisRateLimiter implements IRateLimiter {
  1260→constructor(private redis: Redis) {}
  1261→async check(key: string, limit: number, windowSec: number) {
  1262→const now = Date.now();
  1263→const winStart = now - windowSec * 1000;
  1264→const k = `rl:${key}`;
  1265→const multi = this.redis.multi();
  1266→multi.zremrangebyscore(k, 0, winStart); // чистим старые
  1267→multi.zadd(k, now, `${now}:${Math.random()}`); // добавим текущий
  1268→multi.zcard(k); // считаем в окне
  1269→multi.pexpire(k, windowSec * 1000);
  1270→const [, , count] = await multi.exec();
  1271→const allowed = count <= limit;
  1272→return { allowed, remaining: Math.max(0, limit - count),
  1273→retryAfter: allowed ? 0 : windowSec };
  1274→}
  1275→}
  1276→// In-memory fallback (single-instance dev)
  1277→class MemoryRateLimiter implements IRateLimiter { /* ... LRU + sliding window ... */ }
  1278→export function createRateLimiter(): IRateLimiter {
  1279→return process.env.RATE_LIMIT_BACKEND === "redis" && process.env.REDIS_URL
  1280→? new RedisRateLimiter(new Redis(process.env.REDIS_URL))
  1281→: new MemoryRateLimiter();
  1282→}

  1679→9.3 Миграции базы данных — Backward-Compatible
  1680→Backward-Compatible (expand-contract)
  1681→При падении миграции код откатывается к предыдущей версии, но БД остаётся на новой схеме. Старый код, не
  1682→знающий о новом поле с NOT NULL, падал. Кроме того, при SELECT * лишнее поле могло сломать
  1683→Zod-валидацию. Формальная стратегия Backward-Compatible Migrations (expand-contract).
  1684→Все миграции следуют паттерну expand-contract (расширение — сжатие) в два деплоя. Деплой 1
  1685→(expand): добавляется новое поле с DEFAULT или NULL (разрешено old-коду работать с new-схемой).
  1686→Старый код игнорирует новое поле, новый код начинает его писать. Деплой 2 (contract, через ≥ 1
  1687→неделю): после подтверждения, что весь код использует новое поле и старых инстансов нет, можно
  1688→удалить старое поле или добавить NOT NULL. Категорически запрещено в одном деплое: добавление
  1689→NOT NULL без DEFAULT, удаление колонки, переименование.
